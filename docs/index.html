homepki

A real certificate hierarchy for local development — root CA, intermediates, and server or client leaves, one command each.

Install GitHub

Free and MIT licensed. macOS and Linux.

Three tiers, one command each

Most local TLS setups stop at a self-signed certificate, which falls apart the moment something wants to verify a chain. homepki builds the whole hierarchy and keeps the openssl configs, key material and CA databases straight for you.

Root CAhomepki root-ca -d runlocal.dev
Intermediatehomepki intermediate-ca -d runlocal.dev -n bu1
Server leafhomepki server-cert -d runlocal.dev -i bu1 -s kong-gateway
Client leafhomepki client-cert -d runlocal.dev -i bu1 -c my-client

Each command is synchronous: the files are on disk and usable the moment it returns. Run several intermediates under one root to separate tenants or environments — that is the intended model, and it means one intermediate's leaves are independent of the next.

It verifies its own chains

Every tier has a list that reports expiry, days remaining, and whether the certificate actually chains to its issuer. Verification runs in-process with Go's crypto/x509 — no openssl verify subprocess to parse.

$ homepki server-cert list -d runlocal.dev -i bu1
Server Certificates for runlocal.dev/bu1:
  NAME              EXPIRES     DAYS LEFT  CHAIN
  ────────────────  ──────────  ─────────  ──────────
  kong-gateway.crt  2027-09-18  364        ✓ OK
  stale.crt         2027-04-02  195        ✗ INVALID: x509: certificate signed by unknown authority

Extended key usage is checked too, so a clientAuth certificate will not quietly pass as a server certificate:

  cli1.crt          2027-09-18  364        ✗ INVALID: x509: certificate specifies an incompatible key usage

JSON for scripts

The table is coloured and its columns float with content. Pass -o json when a script needs to make a decision:

homepki server-cert list -d runlocal.dev -i bu1 -o json \
  | jq -e 'all(.[]; .chain_valid)' >/dev/null || echo "broken chain!"

Built for mTLS

Server and client leaves are separate commands with the right extended key usage on each, and the intermediate ships a chain file you can hand to the other side as a trust store.

ROOT=~/.homepki/runlocal-dev

$ROOT/bu1/bu1-intermediate-ca-chain.crt   # intermediate + root — the CA bundle
$ROOT/bu1/server-tls/kong-gateway.crt     # serverAuth leaf + .key
$ROOT/bu1/client-tls/my-client.crt        # clientAuth leaf + .key

Keys are written unencrypted, so nothing prompts for a passphrase and the files load directly into a server config or a Kubernetes secret:

kubectl create secret tls kong-gateway-tls \
  --cert=$ROOT/bu1/server-tls/kong-gateway.crt \
  --key=$ROOT/bu1/server-tls/kong-gateway.key

kubectl create secret generic kong-ca \
  --from-file=ca.crt=$ROOT/bu1/bu1-intermediate-ca-chain.crt

Key files are mode 0600 and CA private/ directories 0700, but the keys themselves are not encrypted. Treat the working directory as sensitive and keep it out of version control.

Subject Alternative Names without the config dance

The leaf's common name is always included as the first DNS SAN. Add more with a repeatable --san; bare values are classified automatically, and a prefix forces the type.

homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway \
  --san kong.local \
  --san 192.168.1.10 \
  --san 'DNS:*.kong.local' \
  --san IP:::1
X509v3 Subject Alternative Name: critical
    DNS:kong-gateway.bu1.runlocal.dev, DNS:kong.local,
    IP Address:192.168.1.10, DNS:*.kong.local, IP Address:0:0:0:0:0:0:0:1

Anything parseable as an address becomes an IP, everything else a DNS entry. DNS:, IP:, email: and URI: prefixes override that, and an invalid address after IP: is rejected rather than silently treated as a hostname.

Quote any SAN containing *. An unquoted --san DNS:*.kong.local is glob-expanded by the shell before homepki ever sees it, and zsh fails the whole command with no matches found.

Your coding agent already knows how to drive it

homepki ships an Agent Skill compiled into the binary. Install it once and AI coding tools stop guessing at flags — and stop walking into the sharp edges below.

homepki skill install          # → ~/.claude/skills/homepki/SKILL.md
homepki skill path             # print the install path
homepki skill install --print  # emit it to stdout, pipe it anywhere

The skill documents the recipe patterns, the JSON output, the teardown story, and the failure modes that are not visible in --help. No download needed; start a new agent session to pick it up.

Questions worth answering up front

Can I use this for production certificates?
No. Keys are unencrypted, validity periods are fixed at 2190 days for CAs and 365 for leaves, and there is no revocation or renewal. This is a local-development CA. Use ACME/Let's Encrypt or your organisation's PKI for anything public-facing.
Every command fails with a config error about a missing equal sign. Why?
You are on macOS's bundled LibreSSL, which does not support the .include directive homepki writes into its generated configs. The error never mentions LibreSSL, which makes it a confusing first run. 
openssl version          # must say OpenSSL 3.x, not LibreSSL
brew install openssl@3
export PATH="$(brew --prefix openssl@3)/bin:$PATH"
Is it safe to re-run a generate command?
No — and this is the sharpest edge. Re-running root-ca or intermediate-ca generates a fresh key and resets that CA's database, orphaning every certificate beneath it, while still reporting success. The tier you touched keeps showing ✓ OK; only the tier below flips to invalid. Build in a fresh working directory, or guard the command by testing for the certificate file first.
How do I re-issue a leaf under the same name?
The intermediate's database allows one certificate per subject, so a same-name re-issue fails — after the new private key has already overwritten the old one, leaving a mismatched pair that chain verification cannot detect. Prefer a new name, or a fresh working directory. The skill documents the database-editing recovery path if you really need the same name back.
How is this different from mkcert?
mkcert installs its root into your OS and browser trust stores, so localhost loads without a warning — less work if that is all you want. homepki never touches a trust store. It wins when you need the real hierarchy: intermediates, client certificates for mTLS, and a CA bundle to hand to a service.
Where does it put things, and how do I start over?
Everything lives under one directory — --workdir, else $HOMEPKI_WORKDIR, else ~/.homepki. There is no delete command, so teardown is rm -rf on that directory. Point HOMEPKI_WORKDIR at a temporary directory for a throwaway PKI.
Does it need anything besides openssl?
No. It is a single static Go binary that shells out to OpenSSL for key generation and signing, and verifies chains itself. Nothing is interactive: openssl is always invoked in batch mode, so no command can block waiting on a passphrase or a DN prompt.

Install

brew tap bcollard/homepki
brew install --cask homepki

Or download a binary for macOS or Linux, amd64 or arm64, from the latest release.

First run

openssl version | grep -q '^OpenSSL' || echo "install Homebrew OpenSSL first"

export HOMEPKI_WORKDIR="$PWD/.pki"     # keep this PKI local and disposable

homepki root-ca         -d runlocal.dev
homepki intermediate-ca -d runlocal.dev -n bu1
homepki server-cert     -d runlocal.dev -i bu1 -s kong-gateway --san kong.local

homepki server-cert list -d runlocal.dev -i bu1

Generate commands are verbose — they echo each openssl invocation and the full signed certificate. Redirect to /dev/null in scripts and confirm with list -o json.
