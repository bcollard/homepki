homepki

Creates a root CA, intermediate CAs, and server or client TLS certificates on your workstation. One command per tier.

Install GitHub

Free and MIT licensed. macOS and Linux. One binary, no OpenSSL needed.

Three tiers, one command each

A self-signed certificate works until something needs to verify a chain of trust. homepki creates all three tiers, keys included, from a single Go binary with nothing else to install.

Root CAhomepki root-ca -d runlocal.dev
Intermediatehomepki intermediate-ca -d runlocal.dev -n bu1
Server leafhomepki server-cert -d runlocal.dev -i bu1 -s kong-gateway
Client leafhomepki client-cert -d runlocal.dev -i bu1 -c my-client

Each command is synchronous: the files are on disk and usable when it returns. Run several intermediates under one root to separate tenants or environments. Leaves under one intermediate are independent of leaves under another.

Chain verification

Every tier has a list subcommand that reports expiry, days remaining, whether the certificate chains to its issuer, and for leaves whether it is revoked. Verification runs in-process with Go's crypto/x509, so there is no tool output to parse.

$ homepki server-cert list -d runlocal.dev -i bu1
Server Certificates for runlocal.dev/bu1:
  NAME              EXPIRES     DAYS LEFT  CHAIN
  ────────────────  ──────────  ─────────  ──────────
  kong-gateway.crt  2027-09-18  364        ✓ OK
  stale.crt         2027-04-02  195        ✗ INVALID: x509: certificate signed by unknown authority

Extended key usage is checked as well, so a clientAuth certificate does not pass as a server certificate:

  cli1.crt          2027-09-18  364        ✗ INVALID: x509: certificate specifies an incompatible key usage

JSON for scripts

The table uses colour and its column widths depend on the content. Use -o json in scripts:

homepki server-cert list -d runlocal.dev -i bu1 -o json \
  | jq -e 'all(.[]; .chain_valid)' >/dev/null || echo "broken chain!"

Client and server certificates for mTLS

Server and client leaves are separate commands, each with the matching extended key usage. The intermediate also gets a chain file to use as a trust store.

ROOT=~/.homepki/runlocal-dev

$ROOT/bu1/bu1-intermediate-ca-chain.crt   # intermediate + root, the CA bundle
$ROOT/bu1/server-tls/kong-gateway.crt     # serverAuth leaf + .key
$ROOT/bu1/client-tls/my-client.crt        # clientAuth leaf + .key
$ROOT/bu1/server-tls/kong-gateway.p12     # with --pkcs12: key + leaf + chain

Keys are written unencrypted, so no command prompts for a passphrase and the files load directly into a server config or a Kubernetes secret:

kubectl create secret tls kong-gateway-tls \
  --cert=$ROOT/bu1/server-tls/kong-gateway.crt \
  --key=$ROOT/bu1/server-tls/kong-gateway.key

kubectl create secret generic kong-ca \
  --from-file=ca.crt=$ROOT/bu1/bu1-intermediate-ca-chain.crt

Key files are mode 0600 and CA private/ directories 0700. The keys themselves are not encrypted, so treat the working directory as sensitive and keep it out of version control.

Subject Alternative Names

The leaf's common name is always the first DNS SAN. Add more with a repeatable --san. Bare values are classified automatically, and a prefix sets the type explicitly.

homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway \
  --san kong.local \
  --san 192.168.1.10 \
  --san 'DNS:*.kong.local' \
  --san IP:::1
X509v3 Subject Alternative Name:
    DNS:kong-gateway.bu1.runlocal.dev, DNS:kong.local, DNS:*.kong.local,
    IP Address:192.168.1.10, IP Address:0:0:0:0:0:0:0:1

client-cert takes --san too, for example a SPIFFE ID as a URI SAN:

homepki client-cert -d runlocal.dev -i bu1 -c my-client \
  --san URI:spiffe://runlocal.dev/ns/default/sa/my-client

Anything that parses as an address becomes an IP entry, everything else DNS. The DNS:, IP:, email: and URI: prefixes override that. An invalid address after IP: is rejected instead of being treated as a hostname.

Quote any SAN containing *. An unquoted --san DNS:*.kong.local is expanded by the shell before homepki receives it, and zsh fails the command with no matches found.

Key types and validity

Every generate command takes --key-type. RSA-2048 is the default; ECDSA is available on P-256, P-384 and P-521, and Ed25519 as ed25519.

homepki root-ca         -d runlocal.dev --key-type ecdsa
homepki intermediate-ca -d runlocal.dev -n bu1 --key-type ecdsa
homepki server-cert     -d runlocal.dev -i bu1 -s kong-gateway --key-type ecdsa-p384

Tiers are independent, so an ECDSA leaf under an RSA intermediate is fine. The signature digest follows the issuing CA's key: SHA-256 for RSA and P-256, SHA-384 for P-384, SHA-512 for P-521. An Ed25519 CA signs with Ed25519, which has no separate digest. An unrecognised value is rejected before anything is written to disk.

Browsers do not accept Ed25519 certificates. Use Ed25519 for service-to-service TLS between Go or OpenSSL 1.1.1+ peers, and RSA or ECDSA for anything a browser opens.

Validity

Every command that signs takes --validity, as days (90d) or a Go duration (24h, 30m). The defaults are 2190 days for CAs and 365 days for leaves.

homepki root-ca     -d runlocal.dev --validity 3650d
homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway --validity 24h
homepki sign        -d runlocal.dev -i bu1 --csr my-service.csr --validity 90d

A certificate never outlives its issuer. A longer value is capped at the issuer's expiry, and the command prints a note when that happens. Short-lived leaves let you test certificate rotation without waiting a year.

Nothing is overwritten by accident

A generate command refuses to replace material that already exists. It exits non-zero, names the files in the way, and changes nothing.

$ homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway
Error: a server certificate named "kong-gateway" already exists under runlocal.dev/bu1:
  ~/.homepki/runlocal-dev/bu1/server-tls/kong-gateway.crt
  ~/.homepki/runlocal-dev/bu1/server-tls/kong-gateway.key

Re-issuing overwrites its private key, so anything already serving that pair
breaks. Pass --force to replace it, or issue under another name

--force on a leaf replaces the key and certificate. There is no certificate database to clean up, so re-issuing under the same name is one command:

homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway \
  --san kong.local --san 10.0.0.5 --force

--force on a CA tier is the destructive one: a new key orphans every certificate below it. The tier you replaced keeps reporting ✓ OK, so check the tier below it.

Trust the root CA

Add the root CA to the system trust store, Firefox and Java, and browsers, curl and JVMs stop warning about certificates issued under it.

homepki trust install   -d runlocal.dev                  # every store available, asks for sudo
homepki trust install   -d runlocal.dev --store nss,java # only Firefox and Java, no sudo
homepki trust status                                     # every root CA in the workdir
homepki trust uninstall -d runlocal.dev
--storeWhere the root goes
systemmacOS: the System keychain. Linux: the anchor directory of Debian, Ubuntu and Alpine, Fedora and RHEL, Arch, or openSUSE, then the bundle is rebuilt with update-ca-certificates, update-ca-trust or trust extract-compat.
nssEvery Firefox profile, and on Linux the Chrome/Chromium NSS database, through certutil (brew install nss, apt install libnss3-tools).
javaThe cacerts keystore of the JDK at $JAVA_HOME, through keytool.
 
$ homepki trust status -d runlocal.dev
Root CA trust:
  runlocal-dev             ✗ partly trusted
      ✓ system /Library/Keychains/System.keychain
      ✓ nss    ~/Library/Application Support/Firefox/Profiles/x1y2.default-release
      ✗ java   /opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home/lib/security/cacerts (alias homepki-runlocal-dev not in the keystore)

Without --store, homepki uses every store it finds: the system store, NSS when a profile and certutil both exist, and Java when JAVA_HOME is set. A store named with --store must be available, or the command fails. status needs no privileges and takes -o json, so a script can check .trusted before asking for a password. The system store, and a cacerts file you cannot write, are changed under sudo.

Trusting the root is not enough on its own: the server must present <name>-intermediate-ca-chain.crt, or a client cannot build the path from the leaf to the trusted root. Restart Firefox and Java processes after installing.

Limit what a CA can issue

Before you trust a root system-wide, restrict it to your own names. A root limited to .klimax.internal cannot vouch for any other site, even if its key leaks.

homepki root-ca -d klimax.internal \
  --name-constraint "permitted;DNS:.klimax.internal"

homepki intermediate-ca -d klimax.internal -n bu1 \
  --name-constraint "permitted;DNS:.bu1.klimax.internal" \
  --name-constraint "IP:10.0.0.0/8"

--name-constraint takes OpenSSL syntax, permitted; or excluded; then DNS, IP, email, or URI, and can be repeated. permitted; can be left out, and IP ranges can be written as CIDR. .klimax.internal matches subdomains only, while klimax.internal also matches the domain itself. Go, macOS, Chrome and Firefox all enforce constraints on a root.

homepki checks every new leaf against its chain before writing it. If a name is not allowed, nothing is written and the command exits non-zero:

$ homepki server-cert -d klimax.internal -i bu1 -s gw --san evil.example.com
Error: x509: a root or intermediate certificate is not authorized to sign
for this name: DNS name "evil.example.com" is not permitted by any constraint

Each constraint only covers its own name type: a DNS constraint on its own leaves IP SANs unrestricted. Every leaf also carries <leaf>.<intermediate>.<domain> as a SAN, so choose a domain inside the constraint. The CA command warns you when it is not.

Sign a request made elsewhere

When a service generates its own key, hand homepki the CSR instead. The private key never leaves the machine that made it.

openssl req -new -nodes -newkey rsa:2048 -keyout my-service.key -out my-service.csr \
  -subj "/O=runlocal-dev/OU=bu1/CN=my-service.bu1.runlocal.dev" \
  -addext "subjectAltName=DNS:my-service.bu1.runlocal.dev,DNS:my-service.local"

homepki sign -d runlocal.dev -i bu1 --csr my-service.csr
homepki sign -d runlocal.dev -i bu1 --csr my-client.csr --type client
homepki sign -d runlocal.dev -i bu1 --csr my-service.csr --out ./my-service.crt

Subject Alternative Names are copied from the request. Every other extension it asks for is ignored: basic constraints, key usage and extended key usage are set by homepki, so a request cannot ask to become a CA.

The intermediate signs only requests carrying its own organization and organizational unit — O= the root CA's literal name, OU= the intermediate name. A mismatch is rejected, and the error prints the exact -subj to use.

Revoke a certificate

revoke adds a leaf's serial number to its intermediate's certificate revocation list and re-signs it. Servers that read the CRL then refuse the certificate.

homepki crl    -d runlocal.dev -i bu1                  # write empty CRLs before anything is revoked
homepki revoke -d runlocal.dev -i bu1 -c my-client --reason keyCompromise
homepki revoke -d runlocal.dev -i bu1 --cert ./my-service.crt
$ROOT/bu1/bu1-intermediate-ca.crl   # the intermediate's CRL
$ROOT/ca/runlocal-dev-root-ca.crl   # the root's CRL
$ROOT/bu1/bu1-crl-chain.crl         # both, for servers that check every tier

nginx and OpenSSL with -crl_check_all need a CRL for every CA in the chain, so give them the chain file. list reports revoked leaves:

  my-client.crt  2027-09-26  364        ✗ INVALID: revoked on 2026-09-26 (keyCompromise)

The CRL file is the only record of revocations. Each CRL is valid for 365 days by default; OpenSSL-based servers reject a CRL past its next update, so run homepki crl again before then, or pass --validity. Re-issuing a revoked name with --force gives it a new serial that is not revoked.

PKCS#12 for Java and Windows

--pkcs12 on server-cert or client-cert also writes <name>.p12, holding the key, the leaf and the CA chain.

homepki server-cert -d runlocal.dev -i bu1 -s kong-gateway --pkcs12
homepki client-cert -d runlocal.dev -i bu1 -c my-client --pkcs12 --pkcs12-password s3cret

keytool -list -keystore $ROOT/bu1/server-tls/kong-gateway.p12 -storepass changeit

The default password is changeit, the same as the JDK's keystores. The file uses the 3DES encoding, which Java, OpenSSL 3, macOS Keychain and Windows all import without extra options. Re-issuing a leaf without --pkcs12 deletes the old bundle, since it holds the old key.

Agent Skill for AI coding tools

homepki includes an Agent Skill compiled into the binary. Install it once so AI coding tools have the flags, the usage patterns, and the failure modes described below.

homepki skill install          # → ~/.claude/skills/homepki/SKILL.md
homepki skill path             # print the install path
homepki skill install --print  # emit it to stdout, pipe it anywhere

The skill covers the usage patterns, the JSON output, how to remove a PKI, and the failure modes that --help does not show. Nothing is downloaded. Start a new agent session to load it.

Common questions

Can I use this for production certificates?
No. Keys are unencrypted, there is no online CA, no ACME and no OCSP, and revocation is published only as CRL files. This is a local-development CA. Use ACME/Let's Encrypt or your organisation's PKI for anything public-facing.
Is it safe to re-run a generate command?
Yes. A generate command refuses to overwrite existing material: it exits non-zero, prints what is in the way, and changes nothing. --force replaces it deliberately. On a CA tier that is still destructive — every certificate below stops verifying, while the tier you replaced keeps showing ✓ OK, so check the tier below it.
How do I re-issue a leaf under the same name?
Pass --force. It writes a new key and certificate over the old pair. The key is regenerated, so anything already serving the old pair has to be reloaded.
How is this different from mkcert?
Both install their root into the system trust store, Firefox/NSS and Java; homepki does it on macOS and Linux, mkcert on Windows too. The difference is the hierarchy: homepki creates intermediates, separate client certificates for mTLS, and a CA bundle to hand to a service. It also enforces name constraints when it issues, revokes certificates with CRLs, and signs requests generated elsewhere. mkcert issues leaves straight from its root.
How is this different from step?
step certificate create can build the same tiers, but you choose the file layout and pass profiles and templates yourself. homepki fixes the layout per domain and intermediate, derives the subjects, and verifies every chain in list. step and step-ca also cover what homepki leaves out on purpose: an online CA with ACME, SSH certificates, and encrypted private keys.
Where does it store files, and how do I start over?
Everything lives under one directory: --workdir, then $HOMEPKI_WORKDIR, then ~/.homepki. There is no delete command, so removing a PKI means rm -rf on that directory. Point HOMEPKI_WORKDIR at a temporary directory for a throwaway PKI.
Does it need OpenSSL?
No. It is a single Go binary: key generation, signing and chain verification use Go's crypto/x509. No command waits for a passphrase or a DN prompt. The only prompt is sudo, when trust install or uninstall changes the system store or a cacerts file you cannot write.

Install

brew tap bcollard/homepki
brew install --cask homepki

Or download a binary for macOS or Linux, amd64 or arm64, from the latest release.

First run

export HOMEPKI_WORKDIR="$PWD/.pki"     # keep this PKI in the project directory

homepki root-ca         -d runlocal.dev
homepki intermediate-ca -d runlocal.dev -n bu1
homepki server-cert     -d runlocal.dev -i bu1 -s kong-gateway --san kong.local

homepki server-cert list -d runlocal.dev -i bu1

Generate commands print each file they write. In scripts, rely on the exit code and check the result with list -o json.
